### 🔴 阻塞

#### 1. Stripe webhook 部署路由漂移：旧版路由 (`/api/stripe/webhook/route.ts`) 仍部署激活

- **位置**：
  - 旧路由文件：`apps/web/src/app/api/stripe/webhook/route.ts`（整个 103 行文件）
  - 文档指示：`docs/DEPLOY_GUIDE.md:378` 写明「Endpoint URL 填写：`https://你的域名.com/api/stripe/webhook`」
  - 新路由文件（fc6591a 新建）：`apps/web/src/app/api/webhook/stripe/route.ts`（236 行，含幂等到期日修复）
- **OWASP 类别**：A04 不安全设计 / A08 软件数据完整性失效
- **STRIDE 类别**：Spoofing + Tampering + Elevation of Privilege
- **CWE 编号**：CWE-1188 Insecure Default Initialization of Resource + CWE-665 Improper Initialization
- **漏洞描述**：
  - `api/stripe/webhook/route.ts:30-46` 接收 `checkout.session.completed` 后用 `session.metadata.userId` 直接升级任意用户为 PRO 且**不写 `subscriptionExpiryDate`**
  - 没有 `WebhookLog` 幂等记录（无 eventId 去重）
  - 没有 `current_period_end` 处理逻辑
  - **结果**：Stripe 付费用户付一次，永不过期（`dashboard.ts:12` 把无到期日的视作永久 PRO）。如果走老路由，fc6591a 的所有 Stripe 修复（写到期日、幂等）无效化
- **攻击场景**：
  1. 攻击者伪造一个 `checkout.session.completed` webhook（`metadata.userId=<victim_id>, tier=pro, subscription=sub_<anything>, customer=cus_<anything>`），因为 STRIPE_WEBHOOK_SECRET 在开发环境如果未配（或 NODE_ENV 设置错误），代码会走 `event = JSON.parse(rawBody)` 分支；signature 不匹配。**在生产环境（NODE_ENV=production）**，只要 STRIPE_WEBHOOK_SECRET 未配即拒绝；但生产部署错配 NODE_ENV 时存在绕过的可能
  2. 即使在生产环境，如果 Stripe Dashboard 的 endpoint URL 仍指向旧 `/api/stripe/webhook`，则：
     - 该路由不幂等，Stripe 重试同一事件 → 多次授权（无害但浪费）
     - 该路由不写 subscriptionExpiryDate → 用户永不过期 → 用户在到期后无限使用 PRO
- **影响**：fc6591a 的关键 Stripe 修复全部失效；用户付费一次性永不过期；管理员误判 PRO 状态；资金损失（无续费扣款）
- **建议**：
  ```ts
  // apps/web/src/app/api/stripe/webhook/route.ts 第一行添加：
  // 老路由已废弃 — 改用 /api/webhook/stripe（含幂等 + 到期日 + 修复）
  // 所有 Stripe Dashboard endpoint 必须指向 /api/webhook/stripe
  return NextResponse.json({ error: "Deprecated. Use /api/webhook/stripe." }, { status: 410 })
  ```
  同时更新 `docs/DEPLOY_GUIDE.md:378` 为 `https://你的域名.com/api/webhook/stripe`。考虑直接删除旧文件，强制迁移。

- **Priority**：**P0（立即）**

#### 2. `metadata.userId` 缺失二次校验，伪造 userId 即可升级任何账号

- **位置**：
  - 新版：`apps/web/src/app/api/webhook/stripe/route.ts:142-167`（`checkout.session.completed`）
  - 旧版：`apps/web/src/app/api/stripe/webhook/route.ts:30-46`
  - Creem：`apps/web/src/app/api/webhook/creem/route.ts:297-313`（`checkout.completed`）仅做 `metadata.userId` → userId
- **OWASP 类别**：A04 不安全设计 / A01 访问控制失效（横向越权）
- **STRIDE 类别**：Elevation of Privilege
- **CWE 编号**：CWE-285 Improper Authorization / CWE-639 Authorization Bypass Through User-Controlled Key
- **漏洞描述**：
  - 三渠道的 webhook 处理器都信任 `metadata.userId` 作为授权标的，不做二次校验
  - 风险路径：签名通过（合规），但 metadata.userId 来自客户端/支付页面创建时塞入的 cookie/session.userId — 创建阶段已从 session 读取，但是跨 step session 切换或并发场景会让原 metadata 与新 session 不一致
  - 旧 Stripe 路由直接 `update({where:{id:userId}, data:{subscriptionTier:'PRO'}})` 不做任何交叉验证
  - 攻击向量：Creem/Stripe 创建结账时可塞任意 `metadata.userId`，若服务端从 body 误读 `req.user.id` 而非 session.user.id，则可指定别人的 userId；当前代码读 `session.user.id` 写入 metadata，但 webhook 在另一 session 中读取 metadata — 没有校验 webhooks 的 metadata.userId 是否曾经绑定当前 customer/subscription
- **攻击场景**：
  - 用户 Alice 登录 → create-checkout → metadata.userId=Alice
  - 攻击者通过 XSS / 网络中间人篡改 metadata.userId 为 Bob（如果前端暴露设置 metadata）→ Creem/Stripe 把这个 checkout 关联给 Alice 的卡
  - webhook `checkout.session.completed` 返回 → 取 metadata.userId=Bob → Bob 被升级 PRO，Alice 付款完成（业务逻辑）
  - 现行代码：`stripe.ts:39-46` 创建时是 `metadata: { userId: session.user.id, tier }`，没暴露在前端，所以这个特定攻击路径目前封堵
  - **但是**：回到 webhook 端，缺乏二级校验，例如：检查 `stripeCustomerId === existing.user.stripeCustomerId` / `creemSubscriptionId === existing.user.creemSubscriptionId` 跨链路一致性。当 metadata 与 customer/subscription 不匹配时拒绝
- **影响**：升级错位 / 内部账号越权
- **建议**：
  ```ts
  // 新增一道交叉校验：
  async function resolveStripeUserId(subscription) {
    const metaUserId = subscription.metadata?.userId
    const customerId = subscription.customer
    const byMeta = metaUserId ? await prisma.user.findUnique({where:{id:metaUserId}, select:{stripeCustomerId:true}}) : null
    const byCust = customerId ? await prisma.user.findUnique({where:{stripeCustomerId:customerId}}) : null
    // 两条链路解析不一致 → 拒绝（payload 异常）
    if (byMeta && byCust && byMeta.id !== byCust.id) {
      throw new Error('metadata.userId 与 customerId 不一致，拒绝升级')
    }
    return byMeta?.id ?? byCust?.id ?? null
  }
  ```
  Creem 端类似做 `userId_by_metadata` + `userId_by_creemSubscriptionId` 双链路交叉。

- **Priority**：**P0（立即）**

#### 3. 旧版 Stripe webhook 在 NODE_ENV 配置错配时可绕过签名验证

- **位置**：
  - `apps/web/src/app/api/stripe/webhook/route.ts:18-23`
  - `apps/web/src/app/api/webhook/stripe/route.ts:117-126`（新路由同样问题）
- **OWASP 类别**：A02 加密失败
- **STRIDE 类别**：Spoofing
- **CWE 编号**：CWE-347 Improper Verification of Cryptographic Signature / CWE-1188 Insecure Default Initialization
- **漏洞描述**：
  ```ts
  if (!STRIPE_WEBHOOK_SECRET) {
    // 开发环境未配 secret — 直接解析（仅 NODE_ENV=development 时允许）
    if (process.env.NODE_ENV === "production") {
      return NextResponse.json({ error: "Webhook secret not configured" }, { status: 500 })
    }
    event = JSON.parse(rawBody)
  } else {
    event = getStripe().webhooks.constructEvent(rawBody, signature, STRIPE_WEBHOOK_SECRET)
  }
  ```
  - 逻辑：当未配置 webhook secret 时，仅 `NODE_ENV === "production"` 阻断；否则允许无签名 JSON.parse
  - **风险**：Vercel 部署可能在某些情况下 `NODE_ENV` 未设置为 `production`（如 Preview 环境、PR 部署）但仍在公网；此时 webhook 端点暴露 + 无签名 = 任何人发 `{"type":"checkout.session.completed","data":{"object":{"metadata":{"userId":"x"}}}}` 即升级 PRO
- **攻击场景**：
  1. 攻击者扫描 CookMate 域名 `*.vercel.app` 列表
  2. 对每个 endpoint POST 上述 JSON 到 `/api/stripe/webhook`
  3. 若 STRIPE_WEBHOOK_SECRET 未配 + NODE_ENV 为 development → 升级成功
  4. Preview 分支（preview.cookmate.ai 之类）默认 NODE_ENV=production 之外的值（Vercel 默认是 production 即使 Preview 也可能）
- **影响**：未授权升级为 PRO（A04 失败 → 资金损失）
- **建议**：
  ```ts
  // 修复：仅当 STRIPE_WEBHOOK_SECRET 完全禁用且明确显式 opt-in 时才允许无签名
  if (!STRIPE_WEBHOOK_SECRET) {
    if (process.env.STRIPE_WEBHOOK_INSECURE === "true" && process.env.NODE_ENV !== "production") {
      event = JSON.parse(rawBody)
    } else {
      return NextResponse.json({ error: "Webhook secret not configured" }, { status: 500 })
    }
  }
  ```
  并删除这条古老的 dev-only 分支。Stripe 推荐所有 webhook 永远要求签名（即使是 dev）。

- **Priority**：**P0（立即）**

### 🟠 严重

#### 4. `WebhookLog` 在签名验证之前持久化原始 body（可能导致日志注入 + 撑爆 DB）

- **位置**：`apps/web/src/app/api/webhook/creem/route.ts:279`、`apps/web/src/app/api/webhook/stripe/route.ts` 类似（新版有，新版无问题；新版 Stripe webhook 未记录 rawBody）
- **OWASP 类别**：A09 日志监控不足 / A03 注入（Log Injection）
- **STRIDE 类别**：Information Disclosure / Repudiation
- **CWE 编号**：CWE-117 Improper Output Neutralization for Logs
- **漏洞描述**：
  ```ts
  // 签名验证前的 received 日志：
  logWebhook("creem", rawEventType, "received", body, eventId ?? undefined)
  ```
  - `body` 是 `await req.text()` 结果，攻击者可控制大小（无 bodySize 限制）
  - 数据库 text 字段无内置大小限制，PostgreSQL text 最大 1GB
  - 后续 `admin/cancel-logs` 端点把 rawBody `JSON.parse` 失败时回退原文显示
- **攻击场景**：
  - 攻击者向 Creem webhook POST 100MB JSON body → 验证失败但已落库 → 数据库行膨胀 / 慢查询 / 备份膨胀
  - 攻击者在 rawBody 中塞入 ANSI 转义序列 → 管理员 `cat` 仓库 dump 时终端渲染不可读
- **影响**：DoS（数据库体积）/ 终端日志注入
- **建议**：
  ```ts
  // 限制日志大小 + 转义控制字符
  const MAX_LOG_BODY = 8 * 1024 // 8 KB
  ```

#### 5. Alipay notify `PENDING → PAID` 后计算"按金额匹配的 months"有歧义窗口

- **位置**：`apps/web/src/app/api/alipay/notify/route.ts:55-71`
- **OWASP 类别**：A04 不安全设计
- **STRIDE 类别**：Tampering
- **CWE 编号**：CWE-1284 Improper Validation of Specified Quantity in Input
- **漏洞描述**：
  ```ts
  const periodMonths: Record<string, number> = { monthly: 1, quarterly: 3, semiannual: 6, annual: 12 }
  let months = 1
  for (const [p, cfg] of Object.entries(PRICING.plans)) {
    if (cfg.cny.amount === order.amount) { months = periodMonths[p] ?? 1; break }
  }
  ```
  - 金额用整数比较（CNY 分），但 `PRICING.plans.monthly.cny.amount = 2000`；假设有人改了 `quarterly.cny.amount = 1999`（活动促销），则 2000 被匹配为 monthly — OK
  - **但**：用户买 monthly 套餐，订单 amount=2000，alipay 通知 → PENDING→PAID → 算 months=1。合预期 ✅
  - **隐患**：`alipay/create/route.ts` 接受 `period: "monthly" | "annual"`，但落库 `amount: price.amount`。如果未来允许 `period: "quarterly"` 而 PRICING 改 quarterly.amount=4900，则仍按 4900 → 3 个月。也 OK
  - **真实问题**：如果"运营临时把 annual 改成 11900→9900" 但忘记同步代码 PRICING，alipay notify 会找不到匹配，仍默认 `months=1`（除非代码 fallback 显式 annual）→ 用户付年费只得 1 月 PRO（这正是上一轮审计的修复点）
  - **当前实现**：默认 `months = 1` → 若没匹配上 fall back 1 月。攻击者角度：用户买年付但金额被运营改 → 仍得 1 月 → 与原修复目标吻合的「fail-closed」更友好，但在 payable mismatch 场景下仍偏向攻击者便宜
  - 改进建议：用 `period` 字段直接读 PaymentOrder 的 `channel`-specific 字段（需要新增 model 列）而非用金额匹配
- **影响**：金额/期间不匹配导致权益错位
- **建议**：在 `PaymentOrder` 加 `period` 字段，`create` 时塞入，直接读这个字段做 `setUTCMonth` 累加。避免金额反查

- **Priority**：**P2（下迭代）**

#### 6. 三渠道 webhook 与 GET 轮询存在双升级路径竞态（Creem）

- **位置**：
  - `apps/web/src/app/api/webhook/creem/route.ts:333-353`（`subscription.paid` 唯一升级点）
  - `apps/web/src/app/api/creem/create-checkout/route.ts:98-138`（GET 路径升级，metadata.period 自算到期日）
- **OWASP 类别**：A04 不安全设计 / A08 软件数据完整性失效
- **STRIDE 类别**：Tampering
- **CWE 编号**：CWE-362 Concurrent Execution using Shared Resource without Proper Synchronization
- **漏洞描述**：
  - `subscription.paid` 用 Creem 官方 `current_period_end_date` + `grantAccess` 幂等（`>= periodEndDate` 跳过）
  - GET 路径用 `metadata.period` + 自算到期日（`setUTCMonth(+1)`/`setUTCFullYear(+1)`）
  - 二者都从 `user.subscriptionExpiryDate > now` 续费累加 — 终态一致 ✅
  - 但当 webhook `subscription.paid` 先到、用户轮询也到时：
    - webhook：写 PRO+expiry=`current_period_end_date`（官方）
    - 轮询：检查 `pendingOrder`，若已 PAID（被 webhook checkout.completed 标记）→ `updateMany PENDING→PAID count=0` → 跳过升级（line 109-115）
    - 假设 checkout.completed 还没到，subscription.paid 已先到：
      - webhook `subscription.paid` → 走 `grantAccess`，但 subscriptionId=NULL → 500 fail-closed 已处理 ✅
      - 但 webhook 与轮询并发，可能都通过 200 升级逻辑两次？
    - 实证：review state machine in detail
    - `creem/route.ts:308 syncSubscription` 写入 `creemSubscriptionId` 与 `userId` 关联，`subscription.paid` 之后的 `findUserIdBySubscriptionId` 可解析 → 升级 ✅
    - GET 路径：line 102 查 `userId+channel+PENDING` 抓的是另一条本地订单（不是 Creem checkout 端），可能与 webhook 重复处理同一订单，但 `updateMany`（line 109）原子，count=0 → 不会双倍升级
    - **所以**：race window 是 webhook 已经升级，但 GET 因为找不到 PENDING 而错算另一笔订单。**理论上双路径都升级同一用户是幂等的**，worst case 是同一笔订单的两笔升级都成功，但 `updateMany` 保护 ✅
  - **真实问题**：GET 路径用 `userId+channel+PENDING` 模糊匹配（line 102），多笔 PENDING 订单会误标记（review #9）。这不是竞态，是逻辑正确性 bug
- **影响**：运营对账困难；偶发数据不准
- **建议**：与新 fc6591a 的 Creem 重写目标吻合 — GET 路径应改为「只查状态，不写库」，由 webhook 统一负责升级

- **Priority**：**P2（下迭代）**

#### 7. `subscription/cancel` 端点面对跨渠道混合订阅的最终一致性依赖 webhook

- **位置**：`apps/web/src/app/api/subscription/cancel/route.ts:55-86`
- **OWASP 类别**：A04 不安全设计
- **STRIDE 类别**：Tampering
- **漏洞描述**：
  - cancel 成功后立即清空 `creemSubscriptionId`/`stripeSubscriptionId`、保留 `subscriptionTier: "PRO"` 与 `subscriptionExpiryDate`
  - dashboard 的 `checkSubscription` 在到期后自动降级
  - 跨场景：如果用户同时有 Creem+Stripe 订阅，cancel 仅清两个 ID。**但 webhook 后续**：Creem 发 `subscription.canceled` → 仅清 creemSubId（已 NULL，无操作）；Stripe 发 `customer.subscription.updated canceled` → 调用 `revokeStripeAccess(userId, true)` → 写 tier=FREE + 清空 expiry + 清空 stripeSubId（已 NULL，无操作）
  - **隐患**：cancel 端点运行时认为「清空两个 subId 后用户已无订阅」，但如果 webhook 还在路上，用户仍然 PRO（正确的"已付费周期不撤回"语义）。如果 webhook 因某种原因**不送达**（Creem 后台故障），用户「理论上已取消」但本地仍显示 PRO — 与上次报告「fail-closed，保留本地订阅ID 便于 webhook 到期降级」的设计一致
  - **fail-closed 优点**：上游取消成功 → 本地 ID 清空，dashboard 的 `cancelled` 字段正确显示 cancelled=true
  - **fail-closed 缺点**：如果上游取消失败（`logCancelAudit` 写 failed），本地 ID 保留 → dashboard 的 `cancelled` 字段为 false → 用户以为还能用 → 直到下次 webhook `subscription.expired` 自然降级，或者重新点 cancel 重试
  - 这是合理的合规语义，但需**确保重试路径清晰**：admin 页有 failed 列表 + reconcile 脚本 ✅
- **影响**：用户体验混淆；如果 fail-closed 后用户持续触发扣款，需 admin 介入补刀
- **建议**：维持现有设计。文档中明确「fail-closed 时用户仍可能扣款，需 admin reconcile」

- **Priority**：**P2（下迭代，需产品对齐）**

## 监控与告警建议

应在以下事件触发告警：

1. **Webhook 验签失败次数暴增**（Creem/Stripe/Alipay 任一）：意味着上游密钥可能泄露或被攻击者试探。建议阈值：1 分钟内失败 > 10 次 → alert
2. **`WebhookLog.status = "failed:signature"`** 单日增长 > 5 次 → alert（与 #1 合并）
3. **`WebhookLog.source = "cancel"` & `status = "failed"`** 任一：意味着有用户取消请求未成功上游执行，资金风险 → alert
4. **同一 IP 在 1 分钟内创建多个 PENDING 订单** → 可能恶意商家钓鱼
5. **`PaymentOrder.status = "PENDING"` 超过 24 小时未变 `PAID/EXPIRED`** → 建议清理脚本
6. **`usageDaily.recipeCount` 突增**（AI 生成次数尖峰）：可能是滥用 / 密钥泄露 / 计费异常
7. **Stripe webhook 同时在两个 endpoint 收到事件**（运营误配的双路由）：监控 `WebhookLog` 中同 `eventId` 在多条 source 上出现
8. **`admin/cancel-logs` 端点请求频率** 异常：可能是 admin email 泄露后被探测
9. **`auth.ts` 中 `failed` 计数骤增**：可能密码/OTP 撞库

告警通道建议：Vercel / Sentry / 自建 AlertManager → Slack / Email。
